# Inzozi Code V0.1.7 — Git approval gate and staging readiness

## Purpose

This slice closes the gap between an Aquila-generated working-tree diff and a reviewable local Git commit, while preparing the staging host for `code-staging.inzozidigital.com`.

It does **not** enable Git push, pull-request creation from the Inzozi runtime, cPanel deployment, or production deployment.

## Human approval flow

1. Aquila Build/Debug works only through guarded workspace tools.
2. The user reviews Git status/diff.
3. If the current branch is protected (`main`, `master`, `production`, `prod`), the user creates a safe branch using one of:
   - `feature/...`
   - `fix/...`
   - `ui/...`
   - `hotfix/...`
   - `deploy/...`
4. `POST /api/v1/workspaces/{workspace_id}/git/commit/prepare` receives the proposed commit message.
5. Inzozi Code runs `git add -N .` so new files are visible in the review diff without staging their contents for commit.
6. The API captures the current branch, HEAD, status and binary-capable diff, then calculates a SHA-256 review fingerprint.
7. Obvious secret-bearing paths are blocked, including `.env`, `.env.*` except `.env.example`, common private-key files, and `secrets/` paths.
8. `git diff --check` must pass.
9. A 15-minute approval ID is returned with the exact reviewed diff.
10. Human approval calls `POST /api/v1/workspaces/{workspace_id}/git/commit/approve` with that approval ID.
11. Before committing, Inzozi Code recomputes the branch/HEAD/status/diff fingerprint. Any change invalidates the approval.
12. Only then does the workspace stage all reviewed changes and create a **local** Git commit.
13. The response explicitly reports `pushed: false` and `remote_write_enabled: false`.

Aquila does not receive the reserved stage/commit actions as ordinary agent tools.

## Alpha limitation

Commit approvals are process-memory state in V0.1.7. They intentionally disappear on API restart and are unsuitable for multi-worker production. When authenticated teams are added, move approvals to Redis/PostgreSQL with user ID, organization ID, audit actor, and expiry.

## Staging host target

- Domain: `code-staging.inzozidigital.com`
- OS: Ubuntu 24.04 LTS
- Recommended initial size: 8 vCPU, 32 GB RAM, 250–500 GB NVMe
- App checkout: `/srv/inzozi-code/application`
- Staging environment: `/srv/inzozi-code/.env.staging` with mode `600`
- Secrets directory: `/srv/inzozi-code/secrets` with mode `700`
- Docker app proxy: `127.0.0.1:8080`
- Docker API port: `127.0.0.1:8000`

The application and API ports bind to loopback so they are not directly exposed on the public VPS interface. Host Nginx owns public HTTP/HTTPS.

## Host bootstrap

Run only on the dedicated staging VPS:

```bash
sudo bash infrastructure/staging/bootstrap-host.sh
```

The bootstrap installs Docker, Docker Compose v2, Nginx, Git and Certbot. It intentionally does not alter firewall rules, DNS, TLS certificates, or secrets.

## Host Nginx

Copy the reviewed template:

```bash
sudo cp infrastructure/staging/host-nginx.conf.template /etc/nginx/sites-available/inzozi-code-staging
sudo ln -s /etc/nginx/sites-available/inzozi-code-staging /etc/nginx/sites-enabled/inzozi-code-staging
sudo nginx -t
sudo systemctl reload nginx
```

Remove the default Nginx site only after confirming it is not needed by another application on the VPS.

## DNS

Create an `A` record at the DNS provider that is authoritative for `inzozidigital.com`:

```text
code-staging.inzozidigital.com -> <STAGING_VPS_PUBLIC_IP>
```

Do not change the main `inzozidigital.com` or cPanel records.

## TLS

Only after DNS resolves to the staging VPS:

```bash
sudo certbot --nginx -d code-staging.inzozidigital.com
```

Then verify automatic renewal:

```bash
sudo certbot renew --dry-run
```

## Required staging environment

Create `/srv/inzozi-code/.env.staging` directly on the server. Do not commit it.

It must contain the non-secret runtime configuration plus the server-side secrets needed by the stack, including database password, `OPENAI_API_KEY`, GitHub App identifiers, and any GitHub App private-key path. Keep the GitHub `.pem` file under `/srv/inzozi-code/secrets` and mount/read it only from the API service.

The replacement OpenAI key created for Inzozi Code must never be pasted into source files, GitHub issues/PRs, browser local storage, or logs.

## Deployment

The deploy script refuses a dirty worktree and does not fetch/pull/merge automatically:

```bash
sudo APP_ROOT=/srv/inzozi-code/application \
  ENV_FILE=/srv/inzozi-code/.env.staging \
  bash infrastructure/staging/deploy-staging.sh
```

A reviewed process or CI job must first put the intended commit in the application checkout.

## Verification checklist

After deployment verify:

- `https://code-staging.inzozidigital.com/health` responds successfully.
- Browser IDE loads over HTTPS.
- API and Docker app ports are not reachable publicly on 8000/8080.
- PostgreSQL and Redis are not host-published.
- GitHub private-repository clone works through the GitHub App.
- `@aquila` and `@chatgpt` show configured after server-side OpenAI key injection.
- Ask/Plan/Design/Review/Deploy do not expose mutation tools.
- Build/Debug create a preflight checkpoint before edits.
- Commit preparation is blocked on `main`.
- Commit preparation blocks `.env`/private-key paths.
- Editing any file after Prepare invalidates the approval.
- Approving an unchanged review creates a local commit only.
- No push or PR happens from the workspace runtime yet.
