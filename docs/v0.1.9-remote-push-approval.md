# Inzozi Code V0.1.9 — Remote Git Push Approval

## Goal

Add the first remote Git write capability without collapsing local commit approval and remote push into one action.

V0.1.9 allows a reviewed, clean, safe-branch local commit to be pushed to its GitHub repository only after a second explicit human approval.

It does not create pull requests, merge branches, force-push, deploy applications, or touch cPanel/production.

## Trust boundaries

### Local commit approval

V0.1.7/V0.1.8 remain unchanged:

`working tree → reviewed diff/tree hash → human approval → local commit`

### Remote push approval

Remote push is separate:

`clean local commit → push review → human approval → short-lived GitHub write token → exact commit push`

The user cannot accidentally approve both actions with one click.

## Push preparation

`POST /api/v1/workspaces/{workspace_id}/git/push/prepare`

Requirements:

- current branch matches the safe Inzozi branch policy: `feature/`, `fix/`, `ui/`, `hotfix/`, or `deploy/`;
- working tree is clean;
- current local HEAD is captured as the exact commit to push;
- workspace repository metadata identifies the GitHub HTTPS repository;
- the configured Inzozi Code GitHub App installation applies to that repository owner.

Prepare creates a 10-minute in-memory approval containing:

- workspace ID;
- repository URL;
- GitHub App installation ID;
- exact branch;
- exact local commit SHA;
- expiry.

No GitHub write token is minted during Prepare.

## Push approval

`POST /api/v1/workspaces/{workspace_id}/git/push/approve`

Before any token is created, Inzozi Code rechecks:

- approval exists and is unexpired;
- working tree remains clean;
- current branch still equals the reviewed branch;
- current HEAD still equals the reviewed commit SHA.

Only then does the API request a short-lived installation token scoped to:

- the single repository;
- `Contents: write`.

The token is sent only to the internal workspace push endpoint. It is never returned to the browser, stored in workspace metadata, embedded in the remote URL, added to Git config, or included in audit records.

## Workspace push

The workspace runtime performs only:

```text
git push --porcelain origin HEAD:refs/heads/<approved-safe-branch>
```

with Git credential helpers disabled and an ephemeral `GIT_ASKPASS` helper.

The runtime independently verifies:

- safe branch name;
- current branch equals approved branch;
- current HEAD equals `expected_head`;
- working tree is clean;
- repository metadata is a GitHub HTTPS URL.

The askpass file is deleted immediately after the push attempt.

No `--force`, `--force-with-lease`, arbitrary refspec, arbitrary remote, shell string, or user-provided Git command is accepted.

## GitHub App permission change

Private clone currently needs only `Contents: read`.

Remote push requires the Inzozi Code GitHub App itself to be configured with **Contents: Read and write** for repositories where push is enabled. Inzozi Code still requests a read-only token for clone and asks for a write token only for an approved push.

This permission change must be reviewed during staging GitHub App configuration. It does not grant pull-request or administration permissions.

## Audit behavior

Workspace audit records may contain:

- repository URL;
- branch;
- commit SHA;
- exit code;
- timeout status;
- whether authentication was used.

They must not contain the installation token or private key.

## Alpha limitation

Push approvals are process-memory state and disappear on API restart. Multi-user production must move these approvals to Redis/PostgreSQL and associate them with authenticated user, organization/project, reviewer identity, IP/session evidence where appropriate, and immutable audit events.

## Acceptance criteria

- API and workspace Python compilation succeeds.
- Existing guarded workspace/security tests remain green.
- Push token models hide secrets from repr/logs.
- Prepare refuses dirty or unsafe branches.
- Approve refuses changed branch/HEAD or expired approval.
- Write token is minted only on Approve and requests `Contents: write`.
- Workspace receives only the exact branch, exact commit SHA and short-lived token.
- Workspace performs no force push.
- Push response reports `pull_request_created: false`.
- No PR, merge, cPanel or production action is introduced.
