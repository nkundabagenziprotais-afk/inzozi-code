# Inzozi Code v0.1.16 — Workspace ownership and isolation foundation

## Goal

Strengthen the private staging security boundary after authentication/RBAC by binding every workspace ID to an authenticated Inzozi organization/user and persisting that ownership and access audit trail in PostgreSQL.

This milestone deliberately does **not** claim production-grade tenant isolation. The workspace runtime is still one shared container and one shared Unix identity/volume. Public staging remains disabled until dedicated per-workspace execution and outbound egress controls are implemented and tested.

## What changes

### Durable ownership registry

The API creates two PostgreSQL tables with non-destructive `CREATE TABLE IF NOT EXISTS` statements when staging ownership enforcement is enabled:

- `workspace_ownership` — workspace ID, organization, owner email/role, repository URL, deterministic namespace, created/deleted timestamps.
- `workspace_access_audit` — durable mutation/denial correlation with actor, role, request ID, event/outcome and non-secret metadata.

The API fails startup closed in staging if the ownership schema cannot be initialized.

### Access rules

- `Platform Owner` and `Org Admin` may access workspaces inside their organization.
- Other roles may access only workspaces whose owner email and organization match their authenticated principal.
- Cross-owner or cross-organization workspace-ID guesses return `404 Workspace not found` so the system does not confirm that another workspace exists.
- Successful workspace creation is registered immediately after the existing workspace runtime returns a workspace ID.
- If ownership registration fails, the newly created runtime workspace is destroyed best-effort and the browser receives a safe `503` instead of an unowned workspace.
- Successful workspace destruction archives the ownership record with `deleted_at`.

Existing RBAC remains authoritative for what an allowed principal can do inside an owned workspace.

### Shared runtime hardening

Until per-workspace execution containers land, the shared workspace service is further constrained with:

- read-only container root filesystem;
- writable `/workspaces` volume only for repository state;
- isolated `/tmp` tmpfs;
- all Linux capabilities dropped;
- `no-new-privileges` enabled;
- explicit memory, CPU and PID ceilings.

These limits reduce blast radius but are **not** a tenant boundary.

## Security limitations that remain

Issue #20 stays open. Before public/team staging:

1. execute each active workspace in a dedicated container/namespace managed by a trusted runner service;
2. never mount the Docker socket inside AI/workspace execution containers;
3. add outbound egress allow/deny policy and test it;
4. add per-workspace disk/time quotas and cleanup TTLs;
5. inject GitHub/OpenAI credentials only into the specific approved action that needs them and never persist them in workspace files;
6. test cross-tenant ID guessing, path traversal, symlink escape, command escape, resource exhaustion and cleanup;
7. use Redis-backed durable login throttling and server-side session registry/revocation (this Issue #20 Redis slice);
8. enable public HTTPS only after escape/exhaustion testing and set `AUTH_COOKIE_SECURE=true`.

## Staging review

After deploying the reviewed branch, run:

```bash
ENV_FILE=/srv/inzozi-code/.env.staging \
  bash infrastructure/staging/workspace-ownership-preflight.sh
```

Expected controls:

- durable ownership/audit registry ready;
- staging ownership enforcement enabled;
- workspace runtime root filesystem read-only;
- all capabilities dropped;
- no-new-privileges active;
- CPU, memory and PID limits non-zero;
- public staging still reported as blocked pending dedicated per-workspace execution and egress controls.

Then run the existing auth and GitHub App preflights again and perform one private-repository connect/disconnect cycle. Do not create a new remote push/PR unless specifically testing those gates.

## Responsive review

No major workspace UI redesign is included in this milestone. Existing UI should still be checked at 360, 430, 768, 1280, 1440 and 1920 after staging deployment to ensure authentication/session controls and repository workflow remain intact.
