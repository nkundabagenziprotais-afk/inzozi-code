# Inzozi Code v0.1.15 — Staging authentication and RBAC foundation

## Business goal

Protect the private Inzozi Code staging workspace with a real sign-in boundary before any public DNS or broader team access is considered. Authentication must not weaken the existing guarded workspace, local-commit, remote-push, or draft-PR approval gates.

This milestone is intentionally an **alpha access-control foundation**. It does not claim production-grade multi-tenant workspace isolation yet.

## User experience

Unauthenticated users see a dedicated Inzozi Code private-staging sign-in screen instead of the repository workspace. The screen explains three trust boundaries in plain language:

- the browser receives an HttpOnly session cookie, not repository credentials;
- the API enforces the signed-in role even when requests are made directly outside the UI;
- merge and production deployment remain disabled.

After sign-in, a compact session control shows the signed-in email and human-readable role with a Sign out action.

## Authentication design

The bootstrap staging account is configured server-side only.

- No plaintext password is stored in Git or `.env`.
- Passwords are hashed with PBKDF2-HMAC-SHA256, 600,000 iterations and a random 16-byte salt.
- Session tokens are signed with HMAC-SHA256 using a separate random server-side secret.
- The browser receives the session in the `inzozi_session` cookie with `HttpOnly`, `SameSite=Strict`, and `Path=/`.
- `AUTH_COOKIE_SECURE=false` is allowed only for the current localhost SSH-tunnel preview. It must be `true` before HTTPS public staging.
- Session lifetime defaults to 480 minutes and can be shortened by environment configuration.
- Login failures are rate-limited in memory for the alpha runtime.

The secret-safe helper `infrastructure/hetzner/configure-staging-auth.sh` prompts for the staging owner email/password locally, derives the password hash locally, generates the session signing secret locally, sends only the derived hash/secret over SSH, and updates the untracked `/srv/inzozi-code/.env.staging` file with mode `0600`.

## API enforcement

Authentication/RBAC is enforced in FastAPI middleware, not only by hiding UI controls.

Protected route families are mapped to explicit permissions:

- workspace reads → `workspace:read`
- workspace creation → `workspace:create`
- file writes → `workspace:edit`
- guarded actions → `workspace:run`
- local branch/commit gates → `git:commit`
- remote push gates → `git:push`
- draft PR gates → `git:pull_request`
- GitHub App readiness APIs → `integration:read`
- Aquila → `agent:use`, with additional mode checks for write/deploy modes

`/health`, `/`, and `/v1/auth/login` are public. `/v1/auth/me`, logout, workspace, agent, Git, and integration routes require a valid signed session when `AUTH_ENABLED=true`.

## Staging activation

Keep the staging app private behind the existing SSH tunnel during this review.

From the local repository on the reviewed branch:

```bash
export SSH_KEY_PATH="$HOME/.ssh/inzozi_code_staging_ed25519"
bash infrastructure/hetzner/configure-staging-auth.sh
```

The helper prompts locally for the bootstrap owner email and password. Do not paste either into chat, GitHub, or shell history.

After syncing/deploying the reviewed branch, run on the host:

```bash
cd /srv/inzozi-code/application
ENV_FILE=/srv/inzozi-code/.env.staging \
  bash infrastructure/staging/auth-preflight.sh
```

Expected preflight properties:

- auth configuration is structurally valid inside the API container;
- `/health` reports `auth_enabled=true`;
- unauthenticated `/v1/auth/me` returns 401;
- unauthenticated `/v1/agent/providers` returns 401;
- no plaintext `AUTH_PASSWORD` exists in the staging env file.

The existing GitHub App preflight can still be run after authentication is enabled because it now verifies the App directly inside the API container instead of bypassing the login gate over HTTP.

## Browser review

Open the existing SSH tunnel and visit `http://127.0.0.1:8080`.

Verify:

1. the sign-in page appears before repository content;
2. wrong credentials produce a generic error and do not reveal account details;
3. correct bootstrap owner credentials open Inzozi Code;
4. the session chip identifies the Platform Owner role;
5. refreshing the page preserves the session;
6. Sign out returns to the sign-in screen;
7. after sign-out, protected API calls return 401;
8. private GitHub repository clone and the three existing Git approval gates still work after signing back in.

Responsive review sizes:

- 360px — sign-in card fits without horizontal scrolling; trust items stack vertically.
- 430px — form controls remain comfortably tappable; session control stays within viewport.
- 768px — sign-in card remains balanced and does not become overly wide.
- 1280px — login hierarchy and spacing remain compact.
- 1440px — no empty decorative dashboard elements are introduced.
- 1920px — card remains intentionally constrained rather than stretching across the screen.

## Security boundaries deliberately unchanged

The following remain disabled or private:

- Aquila stays on `mock-v0` during this milestone.
- No OpenAI API key activation.
- No public staging DNS.
- No merge or auto-merge.
- No production deployment.
- GitHub App private key remains server-side only.
- GitHub App runtime tokens remain action-specific and repository-scoped.

## Known limitation: workspace isolation

Authentication and RBAC do **not** solve the current runtime's shared Unix-user/shared `/workspaces` boundary. The workspace API prevents arbitrary shell and restricts paths/actions, but multiple workspaces still execute under the same workspace service identity and shared volume.

Therefore public/team staging is still blocked until the next isolation milestone introduces stronger per-workspace execution boundaries and tenant ownership checks. Recommended next work:

1. bind every workspace to an authenticated organization/user ownership record;
2. move each workspace execution into a dedicated container/namespace with no Docker socket exposure;
3. add outbound egress policy and per-workspace quotas;
4. persist audit events and workspace ownership in PostgreSQL;
5. add session/audit correlation IDs and durable login throttling in Redis;
6. only then enable HTTPS public staging with `AUTH_COOKIE_SECURE=true`.
