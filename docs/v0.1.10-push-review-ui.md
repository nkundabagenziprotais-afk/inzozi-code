# Inzozi Code V0.1.10 — Push Review UI

## Goal

Expose the V0.1.9 remote Git push approval boundary in the IDE without making push feel automatic or equivalent to local commit approval.

## User flow

1. Review working-tree changes in **Git Review**.
2. Prepare and approve a local commit.
3. Inzozi Code records the resulting local commit SHA for the current UI session.
4. When the working tree is clean and HEAD still equals that approved local commit, **Prepare remote push** becomes available.
5. Prepare calls the remote-push review endpoint. The server locks the exact branch and exact commit SHA for 10 minutes. No write token is minted yet.
6. The UI displays the approved branch, commit and expiry.
7. **Approve remote push** triggers the second human approval.
8. Only the backend may then mint the short-lived GitHub `Contents: write` token and push that exact commit.
9. Success messaging explicitly states that no pull request or merge was created.

## UI invalidation rules

Push approval is cleared when:

- a file is saved;
- Build/Debug starts;
- the safe branch changes;
- a new commit review starts;
- the workspace is disconnected;
- the server rejects the push approval.

The browser is not authoritative; backend branch/HEAD/clean-worktree checks remain mandatory.

## Humanization rules

- Use **Prepare remote push** and **Approve remote push**, never a generic `Push` button.
- Show the local commit SHA before remote write.
- State `No force push · no pull request · no merge` in the remote-write section.
- Keep commit and push approval visually separate.
- Do not display GitHub App tokens, installation IDs or private-key details.

## Responsive review

At 360/430 px the remote-write card stacks vertically and remains reachable through the scrollable Git Review panel. At tablet and desktop widths it remains a compact secondary gate under local commit review rather than dominating the IDE.

Review at 360, 430, 768, 1280, 1440 and 1920 px on staging.

## Acceptance criteria

- TypeScript build passes.
- Existing API/workspace/staging checks remain green.
- Push preparation is unavailable before a successful approved local commit in the current workspace UI session.
- Push preparation is unavailable when the working tree is dirty or the local HEAD changed.
- Push approval shows exact branch/commit/expiry returned by the server.
- Success states explicitly say no PR/merge was created.
- No force-push, PR, merge, cPanel or production-deploy controls appear.

## Next milestone

After staging validates V0.1.10, add pull-request creation as a third explicit workflow using minimum GitHub App PR permission. PR creation should reference the already-pushed safe branch and target a reviewed base branch; merge remains separate and disabled by default.
