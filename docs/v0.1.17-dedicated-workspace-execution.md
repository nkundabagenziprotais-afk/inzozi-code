# Inzozi Code v0.1.17 — Dedicated workspace execution

## Goal

Replace the single shared staging execution container with one dedicated Docker runtime, one named volume and one internal network per active workspace.

This is a security boundary milestone. It does not enable public staging by itself.

## Control-plane design

`workspace-manager` is the only trusted service allowed to access `/var/run/docker.sock`. The API talks to the manager over the internal application network. AI/workspace runtime containers never receive the Docker socket.

Each workspace receives deterministic resources derived from its random 32-character workspace ID:

- `inzozi-ws-<id>` runtime container;
- `inzozi-ws-vol-<id>` project volume;
- `inzozi-ws-net-<id>` private Docker network.

The private network is created with Docker `internal=true`. The manager joins that network only to proxy the guarded runtime API. No two workspaces share the same runtime network, preventing a workspace from directly reaching another workspace container.

The manager accepts control requests only from the API service's resolved internal address. Requests arriving from a workspace network are rejected.

## GitHub egress

Long-lived workspace runtimes have no public internet route.

GitHub access is split into fixed-purpose ephemeral helpers:

- clone helper: validates a GitHub HTTPS URL, performs a shallow clone, writes non-secret metadata, fixes ownership, then exits and is removed;
- push helper: validates the approved safe branch and exact reviewed commit, forces the Git remote URL back to the workspace's recorded GitHub repository, performs a non-force push, then exits and is removed.

GitHub installation tokens are injected only into the helper environment for that action. They are never written into the workspace volume and are not passed to the long-lived runtime container.

The helper network has outbound connectivity, but the helper code exposes no arbitrary command input and accepts GitHub HTTPS repositories only. A future host-firewall allowlist can further restrict this egress at L3/L4.

## Resource and lifecycle limits

Each runtime container is started with:

- read-only root filesystem;
- all Linux capabilities dropped;
- `no-new-privileges`;
- dedicated writable project volume only;
- private `/tmp` tmpfs;
- explicit memory, CPU and PID limits;
- fixed workspace TTL (8 hours by default);
- active-workspace capacity ceiling;
- application-level disk quota measurement after clone and after every mutating runtime request.

If a workspace exceeds the configured disk quota after a mutation, the manager destroys the runtime, network and volume fail-closed to protect staging capacity.

### Disk quota limitation

The current disk quota is application-enforced at guarded action boundaries, not a kernel/filesystem project quota. A malicious or pathological tool could consume host disk during a single action before the post-action measurement runs. Public staging remains blocked until this residual risk is either accepted for the target threat model or replaced with a kernel-backed storage quota / dedicated worker filesystem.

## Recovery and cleanup

Workspace containers carry expiry and ownership-neutral runtime labels. When the manager is recreated it reconnects itself to surviving workspace networks. A janitor checks expiry every minute and removes expired containers, networks and volumes.

Destroying a workspace removes all three dedicated Docker resources. The existing API-side PostgreSQL ownership record is then archived by the ownership middleware.

## Tests and preflight

CI validates:

- manager and runtime Python compilation;
- API/workspace/manager unit tests;
- Compose configuration with the build-only runtime-image profile;
- all staging shell scripts;
- existing Terraform and web build checks.

After staging deployment run:

```bash
ENV_FILE=/srv/inzozi-code/.env.staging \
  bash infrastructure/staging/dedicated-workspace-preflight.sh
```

The preflight verifies:

- the trusted manager has the Docker socket;
- workspace runtimes report zero Docker-socket mounts;
- dedicated execution mode is active;
- TTL, disk and active-workspace limits are non-zero;
- a synthetic internal-network runtime cannot reach `https://github.com`;
- the legacy shared `application-workspace-1` container is absent.

Then rerun authentication, GitHub App and ownership preflights and perform a live private-repository connect/read/disconnect/reconnect cycle.

## Still disabled

- public staging DNS;
- OpenAI credential activation;
- merge/auto-merge;
- production deployment;
- public/team staging approval until the live dedicated-workspace E2E and residual manager/socket + host-disk risk review pass.
